# Приёмка: нагрузочный прогон API (28.09.2026)

НФТ `docs/tz.md` §8 и критерий §11.1: «p95 `/api/v1/cells` < 300 мс, размер ответа в пределах НФТ».

## Как воспроизвести

```bash
cd backend
uv run python tools/loadtest.py --base-url http://127.0.0.1:8000 --requests 60 --concurrency 6
```

Скрипт печатает markdown-таблицу и завершается с кодом 1, если эндпоинт не ответил 200 или p95
превысил бюджет (бюджеты зашиты: 300 мс для `/cells` и `/pois`, 100 мс для `/healthz`).

## Выводы

- **p95 основного эндпоинта `/cells` — 176 мс** при бюджете 300 мс: запас есть, но не двукратный;
  самый тяжёлый запрос — полная сетка res 9 (485 КБ JSON). Повторный прогон (40 запросов на эндпоинт)
  дал p95 172 мс — цифры воспроизводятся.
- **gzip работает:** 57 КБ по сети против 485 КБ полезной нагрузки (≈ 8.5×) — совпадает с оценкой
  Этапа 4 (59 КБ).
- `/pois` и `/healthz` отвечают за десятки миллисекунд, узким местом они не являются.

## Что может понадобиться дальше (не блокирует MVP)

- Прогрев кэша после агрегации (сейчас первый запрос к `/cells` платит за сборку GeoJSON).
- При росте числа городов — кэширование ответов `/cells` на диск/CDN: ответ полностью
  детерминирован для `data_version` и уже отдаёт `ETag`.
- Нагрузочный прогон с большим параллелизмом (например, 50) и с включённым `Cache-Control` на стороне
  клиента — уже ближе к продовому профилю, это часть эксплуатационной приёмки.
