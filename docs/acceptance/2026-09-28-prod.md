## Производительность

### Сторона сервиса (замер на самом сервере)

| Что | Время |
|---|---|
| `/api/v1/cells** (res 9) напрямую в API (`127.0.0.1:8000`) | 37–42 мс |
| `/api/v1/cells** (res 9) через Caddy с TLS | 78–84 мс |
| Повторный запрос с `If-None-Match` | 50–55 мс, **0 байт** тела (ответ 304) |

То есть бюджет НФТ «p95 `/api/v1/cells` < 300 мс» на стороне сервиса выполняется с запасом.

### Внешний синтетический прогон (40 запросов на эндпоинт, параллелизм 6)

| Эндпоинт | p50, мс | p95, мс | p99, мс | RPS | Передано |
|---|---:|---:|---:|---:|---:|
| `/api/v1/cells` res 9 | 220 | 690 | 699 | 21 | 56.9 КБ |
| `/api/v1/cells` res 9, повторный визит (304) | **130** | **240** | 312 | 42 | 0 КБ |
| `/api/v1/cells` res 8 | 54 | 79 | 81 | 105 | 9.2 КБ |
| `/api/v1/pois` | 24 | 77 | 82 | 184 | 1.2 КБ |
| `/healthz` | 15 | 21 | 27 | 363 | 0 КБ |

Повторный визит (обычный сценарий браузера: данные валидируются по ETag) укладывается в бюджет;
первый запрос полной сетки в бюджет не укладывается — и это не CPU сервера (см. замеры выше), а передача
~500 КБ полезной нагрузки по внешнему каналу до машины, с которой запускался прогон (две серии прогонов
дали p95 522 и 690 мс при неизменной серверной части).

Что уже улучшено по итогам этих замеров:

- **число воркеров API стало параметром** `GEOPULS_WORKERS` (по умолчанию 2): до этого один процесс
  на двух ядрах оставлял половину CPU простаивающей — p50 упал с 304 до 220 мс, RPS вырос с 18.9 до 21.2
  (на повторных запросах — с 26.3 до 41.5);
- проверено условное кэширование: `ETag` + `Cache-Control: public, max-age=3600`, повторный визит — 304.

Что делать дальше (после MVP): уменьшать саму полезную нагрузку — сейчас это полноценные полигоны
1507 ячеек; компактнее отдавать центры и `count` (или векторные тайлы), плюс рассмотреть CDN для
статики.

## Дефекты, найденные при приёмке (и что с ними сделано)

1. **404 при клике по ячейке сразу после смены разрешения по зуму.** Состояние уже переключилось на
   `res 8`, а на экране был отрисован прежний слой `res 9`; запрос списка объектов уходил с чужим `res`,
   и API отвечал 404 (ячейки с таким индексом в этой сетке нет). Исправлено: разрешение берётся из
   H3-индекса кликнутой ячейки (`resolutionOfCell`), есть юнит-тест и регрессионная проверка в проде.
   Нашлось именно браузерной проверкой прода.
2. **Один воркер API на двухядерной машине** — половина CPU простаивала при сериализации GeoJSON.
   Исправлено параметром `GEOPULS_WORKERS` (по умолчанию 2), эффект измерен (см. выше).
3. **Мониторинг сообщал о превышении порогов, но не считал это сбоем**: тревога печаталась, а код
   возврата оставался нулевым, то есть cron не заметил бы проблему. Исправлено (провалы диска, памяти и
   устаревание данных попадают в счётчик), проверено на самом сервере.
4. **`update.sh` при первом запуске не находился на сервере** — артефакт порядка операций: сначала
   нужно распаковать новый архив, потом запускать скрипт из него. Зафиксировано в `docs/deploy.md`.
5. Ранее в тот же день, локально: **404 `/favicon.ico`** (исправлено иконкой) и отсутствие кэш-валидации
   заголовков в проверке — оба случая описаны в отчёте Lighthouse.

## Что осталось за пределами этой приёмки

- **Внешний uptime-наблюдатель.** Свой монитор живёт на том же сервере, поэтому падение машины он не
  заметит. Рекомендация: UptimeRobot или Zabbix провайдера (агент уже работает, порт 10050).
- **Алерты требуют вебхука.** `GEOPULS_ALERT_WEBHOOK` не задан: сейчас тревоги видны в
  `/var/log/geopuls/*.log` и в коде возврата. Почтовые уведомления невозможны: порт 25 закрыт
  провайдером. Формат Telegram поддерживается, достаточно указать URL бота.
- **Реальное плановое обновление данных ещё не проходило**: cron настроен, первая задача — воскресенье
  02:30. Отдельного прогона `refresh-data.sh` с полным импортом PBF на этом сервере не было (2 vCPU /
  3.9 ГБ, импорт держит индекс локаций osmium); в скрипте есть защита по свободной памяти и откат на
  пересборку агрегатов с тревогой.
- **Пароль root из выдачи провайдера** передан открытым текстом — его нужно сменить и перейти на
  SSH-ключи (шаги в `docs/deploy.md`, раздел «Безопасность»).
- Домен `<IP>.sslip.io` — технический. Переезд на свой домен описан и занимает одну переменную.
