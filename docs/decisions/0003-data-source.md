# ADR 0003. Источник данных OSM

Дата: 28.09.2026. Статус: принято.

## Контекст

Нужны POI (кафе, аптеки, магазины и т. д.) по городу РФ. В ТЗ v0.1 источником был только Overpass API
(`httpx` + `osmnx`).

## Проблема

Проверка 28.09.2026 из рабочей сети:

- `https://overpass-api.de/api/interpreter` (POST, bbox Томска) → `runtime error: ... Dispatcher_Client::request_read_and_idx::timeout. The server is probably too busy to handle your request.`
- зеркало `https://overpass.kumi.systems/api/interpreter` → таймаут запроса (curl exit 28).

Дополнительно Overpass не даёт воспроизводимой версии данных: дата выгрузки не фиксируется,
а запросы одного и того же bbox в разное время дают разный результат. Для продукта, который показывает
пользователю «данные на <дата>», это неприемлемо.

## Решение

1. **Основной источник — Geofabrik**: `siberian-fed-district-latest.osm.pbf`
   (≈ 557 МБ, 584 449 957 байт на 27.09.2026, обновляется ежедневно; есть вариант `.gpkg.zip`).
   Чтение: `pyogrio` (GPKG) или `pyosmium` (PBF).
2. **Overpass API — резерв** для точечных догрузок и отладки: POST + экспоненциальные ретраи +
   кэш сырых ответов на диск (чтобы однажды успешный ответ не запрашивался повторно).
3. **Файл выгрузки фиксируется**: имя (`...-260927.osm.pbf`), дата и контрольная сумма пишутся
   в `import_runs` и попадают в `data_version` — именно это значение видит пользователь в интерфейсе.
4. Скачанные PBF в git не попадают (`.gitignore`: `*.osm.pbf`, `data/raw/*`).

## Последствия

- Импорт воспроизводим: одна и та же выгрузка → один и тот же результат (идемпотентность тестируется в CI).
- Нет зависимости от доступности чужого API в момент запуска парсера.
- Недельный импорт 557 МБ файла: скачивание однократное, разбор — минуты на город.
- Если Geofabrik недоступен, остаётся апстрим OSM (planet/`osmosis`-выгрузки) или Overpass как резерв.
