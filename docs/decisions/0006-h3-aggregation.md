# ADR 0006. Агрегация H3: полная сетка, точная площадь, квантильные классы

Дата: 28.09.2026. Статус: принято.

## Контекст

Нужна тепловая карта плотности POI по городу. Требования ТЗ: показывать **пустые** зоны (это и есть
продукт), считать цвет по плотности (не по количеству), одинаково масштабировать шкалу для web-,
PNG- и PDF-представлений, обновляться вместе с данными.

## Решения

**1. Сетка строится по полигону города, а не по bbox** (`h3.polygon_to_cells`, центры ячеек внутри
контура). Плюс к покрытию добавляются ячейки POI внутри полигона: если объект стоит у самой границы,
центр его ячейки может оказаться за контуром, и объект выпал бы из агрегата. В Томске так добавилось
2 ячейки на res 8 и 0 на res 9.

**2. POI фильтруются по полигону** (`ST_Contains`), а не по bbox. Проверка на реальных данных:
из 2 100 импортированных POI внутри полигона Томска оказалось **1 976** — 124 объекта стояли в bbox,
но за границей города. Без этого фильтра тепловая карта «размазывалась» бы за пределы города.

**3. Площадь каждой ячейки считается точно** (`h3.cell_area`), плотность = `poi_count / area_km2`.
Честное уточнение: разброс площадей ячеек H3 **до 1.99×** — глобальное свойство сетки, но в масштабе
одного города он мал (в Томске res 9: 0.1169–0.1171 км², то есть 0.2%). Расчёт по фактической площади
оставлен, потому что он корректен по определению и не зависит от того, где расположен город.

**4. Пишутся все ячейки × все категории, включая пустые** (`poi_count = 0`): 1507 ячеек × 8 категорий
= 12 056 строк для res 9. Пустая ячейка хранится как данные, а не как отсутствие данных, — иначе
«карты пустых зон» не получить (агрегация `GROUP BY` по POI пустые ячейки теряет).

**5. Границы классов легенды считаются на бэкенде** (`density_breaks`), квантильная шкала по непустым
ячейкам. Если квантили совпадают (плотность дискретна: один объект в ячейке res 9 ≈ 8.5 POI/км²),
происходит переход на равномерную шкалу — иначе легенда показывала бы пустой класс
(«8.5–8.5»).

## Альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Хранить только непустые ячейки | Прямо противоречит продукту: пустые зоны — главный ответ сервиса |
| Считать плотность по средней площади ячейки | Дешевле, но даёт неверную плотность при значимом разбросе площадей |
| Классы легенды на клиенте | Шкала разошлась бы между web, PNG и PDF-отчётом |
| Плотность по `grid_disk(k)` вместо радиуса | Точность ±половина ячейки; для «плотности в ячейке» не нужно, для радиуса 500 м в фазе 2 — `ST_DWithin` |

## Проверка на реальных данных (Томск, выгрузка 27.09.2026)

| Показатель | Значение |
|---|---|
| Площадь полигона / сумма площадей ячеек res 9 | 176.8 / 176.4 км² (**−0.2%**) |
| Ячейки res 9 / res 8 | 1 507 / 217 |
| Непустых ячеек res 9 | 341 (22.6%), то есть **78% города — «пустые зоны»** |
| Строк в `cell_stats` (res 9 + res 8) | 12 056 + 1 736 |
| POI в полигоне | 1 976 (по 8 категориям, сумма совпадает со статистикой) |
| Время агрегации | 0.2 с вычислений, 2.5 с с записью в БД |

## Последствия

- Агрегация пересобирается целиком (delete + insert по городу и разрешению) в одной транзакции:
  идемпотентно и безопасно для читателей API.
- `city_cells` и `cell_stats` не зависят от того, как получены POI: пересборка после нового импорта
  занимает секунды.
- Для 4 городов первой волны объём статистики — порядка 50–60 тысяч строк: кэшируется и отдаётся
  статикой (Этап 4).
