# ADR 0011. Стек в контейнерах: миграции при старте и порядок запуска

Дата: 28.09.2026. Статус: принято.

## Контекст

`docker-compose.yml` с самого начала описывал `db`, `api` и `web`, но фактически запускался только
контейнер БД: `tools/dev-up.ps1` поднимал в Docker только PostgreSQL, а API и фронтенд работали
нативно. Итог — «в докере только БД», деплой не воспроизводился одной командой, а Dockerfile'ы
не собирались годами (регрессии в них могли дойти до прода).

При переводе стека в контейнеры выяснилось, что «просто `docker compose up`» не работает по трём
причинам, каждая из которых ломает контейнер:

1. **Свежий том БД пуст**: без миграций `/readyz` отдаёт 503, без справочника категорий пуст
   `/api/v1/meta/categories`.
2. **`httpx` лежал в dev-зависимостях**, хотя его использует продакшн-код (`geopuls.importers.boundary`
   тянет границу города из Nominatim). В образе с `uv sync --no-dev` сид падал с `ModuleNotFoundError`.
3. **`libexpat.so.1`** нужен расширению `pyosmium` (чтение OSM PBF) во время работы, а не только при
   сборке: установка `libexpat1-dev` в builder-этапе проблему не решала.

Плюс классика Windows: `docker-entrypoint.sh` с CRLF-переводами строк ломает shebang
(`exec ./docker-entrypoint.sh: no such file or directory`), хотя файл на месте.

## Решения

**1. Контейнер API сам приводит БД в рабочее состояние.** `backend/docker-entrypoint.sh`:
`alembic upgrade head`, затем `python -m geopuls.seed --skip-city` (идемпотентный справочник
категорий), затем `exec uvicorn`. Повторный запуск безопасен. Данные города и POI остаются
отдельными командами: выгрузка OSM (557 МБ) в образ не входит, а её импорт — по расписанию/вручную
(`docker compose run --rm api python -m geopuls.importers.poi --pbf /data/raw/...`), папка `data/`
хост-машины смонтирована в `/data`. Флаг `GEOPULS_AUTO_SEED=0` отключает сид при необходимости.

**2. Порядок запуска задают healthcheck'и, а не `sleep`.** `db` — `pg_isready`, `api` — `/healthz`
(проверка живости процесса, а не готовности БД), `web` — HTTP-запрос к `/`. `web` ждёт
`api: condition: service_healthy`, `api` — `db: condition: service_healthy`. Так `docker compose up -d`
не отдаёт «зелёный» стек, в котором фронтенд уже открыт, а API ещё не отвечает.

**3. Бэкенд-образ многоступенчатый.** Компилятор и `-dev`-пакеты (`build-essential`, `cmake`,
`libexpat1-dev`, `zlib1g-dev`, `libbz2-dev`) нужны только для сборки `pyosmium`; в рабочий образ
попадают только `.venv`, исходники, миграции и точка входа, а из системных библиотек — `libexpat1`.
`httpx` перенесён в основные зависимости `pyproject.toml`: код импортёров — часть продакшена.

**4. LF для скриптов.** `.gitattributes` (`* text=auto eol=lf`) даёт LF в рабочей копии, но файл,
созданный до первого коммита, может попасть в контекст сборки с CRLF. Поэтому в Dockerfile перед
`chmod +x` стоит `sed -i 's/\r$//'` — сборка перестаёт зависеть от того, как файл выгружен на Windows.

**5. Одна команда на запуск и остановку.** `tools/docker-up.ps1` собирает образы, поднимает стек,
ждёт готовности (health) и печатает ссылки; флаги: `-Prod` (профиль caddy с авто-TLS), `-NoBuild`,
`-ApiPort`/`-WebPort` (порты прокидываются в compose, за ними следуют CORS API и базовый URL
фронтенда). `tools/docker-down.ps1` останавливает стек, `-Purge` дополнительно удаляет том с данными.

**6. Один домен без встраивания адреса в сборку.** Пустое `NEXT_PUBLIC_API_BASE_URL` теперь означает
«тот же origin» (`lib/api.ts`): за Caddy фронтенд и API живут на одном домене, поэтому переезд на
другой адрес не требует пересборки web-образа.

**7. CI собирает образы.** Отдельная задача `images` (`docker compose build api web`): поломка
Dockerfile видна на пуше, а не при деплое. Это прямая реакция на исходную проблему.

## Проверки

- Образы `geopuls-api` и `geopuls-web` собираются (`docker compose build`), импорт внутри образа
  проверен: `python -c "import osmium, h3, httpx"` (это ловит и libexpat, и dev/prod-разделение).
- Стек поднимается и доходит до healthy: `db`, `api`, `web` (лог API: миграции → сид категорий →
  Uvicorn).
- `curl /healthz` и `/readyz` → 200, `/api/v1/meta/cities` отдаёт реальный Томск (176.8 км²,
  версия данных `2026-09-27`) из того же тома, что использовался при разработке.
- E2E-набор Playwright (7 проверок: подложка и тепловой слой, клик по ячейке, ссылка, буфер,
  PNG/CSV) проходит против контейнерного стека — то есть проверяется production-сборка Next
  в контейнере, а не dev-сервер.
- Цикл `docker-down.ps1` → `docker-up.ps1` проверен: данные БД сохраняются (том не удаляется).

## Последствия

- `pwsh -File tools/docker-up.ps1` — воспроизводимый стек: та же последовательность, что на VPS.
- Миграции выполняет контейнер API при старте: это рассчитано на одну реплику API. При переходе на
  несколько реплик миграции нужно вынести в отдельный шаг (`migrate`-джоба), иначе `alembic upgrade`
  будет выполняться конкурентно.
- Данные остаются вне образов: `db` — том `pgdata`, выгрузки OSM — каталог `data/` на хосте.
