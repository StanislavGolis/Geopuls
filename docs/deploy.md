# Развёртывание ГЕОПУЛЬС на сервере

Прод: **https://201.34.158.13.sslip.io** — VPS `201.34.158.13` (нода `kvmnvm-1209`), Ubuntu 26.04,
2 vCPU, 3.9 ГБ RAM, 45 ГБ диска. Сертификат Let's Encrypt выпускает Caddy автоматически.

Кратко о контуре: наружу смотрит только Caddy (80/443), БД, API и фронтенд публикуются на
`127.0.0.1`; секреты живут в `/opt/geopuls/.env` (права `600`) и в git не попадают.

## Что где лежит

| Путь | Что это |
|---|---|
| `/opt/geopuls` | код коммита (развёрнут из `git archive`, git-истории на сервере нет) |
| `/opt/geopuls/.env` | конфигурация: домен, пароль БД, число воркеров, выгрузка для cron |
| `/opt/geopuls/backups` | дампы БД (`geopuls-<дата>.dump`), храним 14 дней |
| `/var/log/geopuls` | логи cron-задач и `monitor.json` (машиночитаемая история проверок) |
| `/etc/cron.d/geopuls` | расписание: бэкап, проверка копии, мониторинг, обновление данных |
| `/opt/geopuls/data` | выгрузки OSM для обновления данных (`data/raw/*.osm.pbf`) |

Скрипты эксплуатации — `infra/ops/`: `install-docker.sh`, `install-swap.sh`, `bootstrap.sh`, `deploy.sh`,
`update.sh`, `backup.sh`, `verify-backup.sh`, `monitor.sh`, `refresh-data.sh`, `watch-refresh-memory.sh`,
`cron.geopuls`.

## Первый деплой (с нуля)

```bash
# 1. Docker и compose, swap (один раз)
bash infra/ops/install-docker.sh
bash infra/ops/install-swap.sh          # 2 ГБ: импорт выгрузки пиково ест память, swap на VPS нет

# 2. Локально: архив коммита и прод-конфигурация
git archive --format=tar.gz -o geopuls-src.tar.gz HEAD
# .env готовится по образцу .env.example (обязательно: DOMAIN, POSTGRES_PASSWORD,
# пустой NEXT_PUBLIC_API_BASE_URL, GEOPULS_WORKERS)

# 3. Скопировать на сервер: архив, .env и, при желании, дамп данных
scp geopuls-src.tar.gz prod.env root@<IP>:/tmp/

# 4. Подготовка каталога и запуск
mkdir -p /opt/geopuls/backups
install -m 600 /tmp/prod.env /opt/geopuls/.env && sed -i 's/\r$//' /opt/geopuls/.env
tar -xzf /tmp/geopuls-src.tar.gz -C /opt/geopuls
cd /opt/geopuls
ARCHIVE=/tmp/geopuls-src.tar.gz DUMP=/tmp/geopuls-init.dump bash infra/ops/bootstrap.sh
```

`bootstrap.sh` собирает образы, поднимает прод-профиль (`docker compose --profile prod up -d`),
ждёт healthcheck'и, восстанавливает данные из дампа (если передан) и ставит cron.

## Обновление до новой версии

Релиз помечается аннотированным тегом, на сервер уезжает архив тега (для срочной правки можно взять
`HEAD`, но в прод правильнее пускать только помеченное состояние):

```bash
# локально
git tag -a v0.1.1 -m "кратко: что вошло в релиз"   # если релиз ещё не помечен
git push origin v0.1.1
git archive --format=tar.gz -o geopuls-src.tar.gz v0.1.1
scp geopuls-src.tar.gz root@<IP>:/tmp/

# на сервере
cd /opt/geopuls && tar -xzf /tmp/geopuls-src.tar.gz && chmod +x infra/ops/*.sh
ARCHIVE=/tmp/geopuls-src.tar.gz bash infra/ops/update.sh
```

Реестра образов нет: `update.sh` собирает образы на сервере из исходников коммита, поэтому
`docker compose pull` не используется. Скрипт сначала снимает бэкап, затем пересобирает и
перезапускает контейнеры; данные в томе `pgdata` не трогаются. Правки только в скриптах (`infra/ops`)
пересборки не требуют — достаточно распаковать архив.

**Версия в `/version` проставляется автоматически.** В архиве лежит файл `VERSION` с подстановкой git
(`export-subst` в `.gitattributes`): `git archive` записывает туда коммит, дату и ссылки, из которых
собран архив (например `refs=(HEAD -> main, tag: v0.1.1)`), а `update.sh` переносит коммит в
`GEOPULS_GIT_SHA`. Проверить, что именно развёрнуто: `curl -fsS https://<домен>/version`.

**`update.sh` перезапускает Caddy.** После пересоздания контейнера `api` прокси какое-то время
отдаёт 502: он держит соединение с прежним адресом контейнера. Скрипт перезапускает Caddy и проверяет
публичный `/healthz` — это ловушка, найденная на проде, а не теоретическая.

**Порядок при изменениях схемы.** Миграции применяет entrypoint контейнера `api` при старте, поэтому
обновление кода и обновление схемы — один шаг. Перед накатом на прод полезно «отрепетировать»:
снять дамп (`infra/ops/backup.sh`), развернуть его в отдельную базу (`db-restore.ps1` с `-KeepRestored`
или `verify-backup.sh` с `KEEP_CHECK=1`) и прогнать `alembic upgrade head` на копии. На Этапе 8 так и
делалось: 13 792 строки до и после, слой и категории на месте.

**Откат**: положить архив предыдущего тега и повторить `update.sh` — данные остаются на месте.

**Одной командой:** `pwsh -File tools/deploy.ps1` — собирает архив коммита, загружает его, запускает
`update.sh`, ждёт, пока `/version` покажет ожидаемый коммит, и прогоняет `prod-check.ps1`. Доступ к
серверу — по ключу (`VPS_KEY`, по умолчанию `~/.ssh/id_ed25519`).

## Домен и TLS

Сейчас используется `<IP>.sslip.io`: сервис `sslip.io` отдаёт публичный DNS для такого имени, поэтому
Let's Encrypt выдаёт обычный (не самоподписанный) сертификат без покупки домена. Caddy продлевает его
сам (в логах — `certificate obtained successfully`).

Переезд на свой домен — одна переменная:

1. A-запись домена → `201.34.158.13` (порты 80/443 должны быть открыты).
2. `DOMAIN=geopuls.example.ru` в `/opt/geopuls/.env`.
3. `docker compose --profile prod up -d` — Caddy выпустит сертификат на новое имя.
4. Фронтенд пересобирать не нужно: `NEXT_PUBLIC_API_BASE_URL` пуст, запросы идут на тот же origin.

## Данные

- **Начальное наполнение**: восстановление дампа (`bootstrap.sh` с `DUMP=...`).
- **Плановое обновление**: cron `infra/ops/refresh-data.sh` — воскресенье, 02:30. Скачивает свежую
  выгрузку Geofabrik (`curl -z`, только если появилась новее), затем `python -m geopuls.refresh`
  (справочники → POI → агрегация). Если свободной памяти меньше порога (по умолчанию 2000 МБ),
  полный импорт пропускается с тревогой в вебхук, а агрегаты пересобираются.
- **Сколько это занимает** (замер на проде 28.09.2026, выгрузка Сибирского ФО 557 МБ, 2 vCPU):
  скачивание ≈ 2 мин, скан ≈ 40 мин, агрегация 0.2 с — полный цикл ≈ 42 мин, поэтому окно 02:30
  закрывается раньше бэкапа в 03:20. Пик памяти контейнера импорта 1.78 ГиБ, минимум свободной
  памяти на хосте 0.95 ГиБ. Чтобы перемерить, запустите рядом
  `nohup bash infra/ops/watch-refresh-memory.sh /var/log/geopuls/refresh-memory.log &`.
- **Ручной запуск**: `bash infra/ops/refresh-data.sh --skip-import` (быстро, только агрегаты).
- **Права на каталог выгрузки.** Плановое обновление скачивает PBF от имени root на хосте, а импорт
  выполняется в контейнере от непривилегированного пользователя `app` (uid 1000) и пишет рядом с
  выгрузкой файл кандидатов. Поэтому `refresh-data.sh` перед импортом отдаёт `data/raw` и сам PBF
  пользователю контейнера (uid/gid берутся из работающего контейнера). Если запускать импорт вручную
  из контейнера без этого шага, он упадёт с `PermissionError` — первый прогон на проде именно так и
  упал, поэтому это уже встроено в скрипт.

## Бэкапы и проверка восстановления

```bash
bash infra/ops/backup.sh                 # дамп в ./backups, ротация 14 дней (KEEP_DAYS)
bash infra/ops/verify-backup.sh          # восстановление в отдельную БД + сверка числа строк
KEEP_CHECK=1 bash infra/ops/verify-backup.sh   # оставить проверочную базу для разбора
```

`verify-backup.sh` возвращает ненулевой код при расхождении — это и есть «проверка выполнена, а не
заявлена» (DoD §11.1). Cron запускает её 1-го числа каждого месяца.

## Мониторинг и алерты

`monitor.sh` (cron каждые 5 минут) проверяет:

- `/healthz`, `/version`, `/readyz` — через публичный адрес, то есть тем же путём, что и пользователь
  (после двух неудачных прогонов подряд считается, что сервис недоступен ≥ 5 минут);
- свежесть данных: `data_version` из `/api/v1/meta/cities` старше 14 дней — тревога;
- диск и память > 85 %;
- все контейнеры в состоянии `running`;
- возраст последнего бэкапа (> 48 часов — тревога).

Результат пишется в `/var/log/geopuls/monitor.log` и `monitor.json`, при сбое — ненулевой код (cron
доставит письмо) и сообщение в вебхук, если задан `GEOPULS_ALERT_WEBHOOK` (поддерживается формат
Telegram `{"text": ...}`).

**Чего пока нет**: внешнего uptime-наблюдателя, который заметит падение всей машины. Рекомендация:
нацелить внешний сервис (UptimeRobot или Zabbix провайдера — агент уже работает на порту 10050) на
`https://<домен>/healthz` и `/readyz`. Порт 25 у провайдера закрыт, поэтому почтовые алерты из скриптов
не рассматриваются — только вебхук.

## Расписание (cron)

| Когда | Что | Лог |
|---|---|---|
| каждые 5 минут | мониторинг | `/var/log/geopuls/monitor.log` |
| ежедневно 03:20 | бэкап БД | `backup.log` |
| 1-го числа 04:20 | проверка восстановления | `verify-backup.log` |
| воскресенье 02:30 | обновление данных | `refresh.log` |

## Проверки после деплоя

```powershell
pwsh -File tools/prod-check.ps1 -ExpectedSha <коммит>   # healthz/readyz/version, слои, числа ячеек, браузер
pwsh -File tools/prod-check.ps1 -SkipBrowser            # быстрая проверка без браузера
```

Скрипт печатает по строке на проверку (коды, время ответа, числа слоя, проблем в браузере) и падает с
ненулевым кодом, если что-то не сошлось. Точечные `curl` к эндпоинту нужны только при разборе
инцидента: в обычном цикле их заменяет `prod-check`.

Разовые прогоны, которые не входят в рутину (отчёты — `docs/acceptance/`):

```bash
cd backend && uv run python tools/loadtest.py --base-url https://<домен> --requests 40 --concurrency 6
npx lighthouse "https://<домен>/?city=tomsk&category=cafe" --chrome-flags="--headless=new"
```

Правила вывода (почему команды запускаются именно так) — в README, раздел «Проверки и деплой одной
командой».

Флаг `debug=1` в URL обязателен для браузерных проверок: ссылка на карту (`window.__geopulsMap`) в
продакшене отдаётся только с ним (ADR 0009). `prod-diagnose.mjs` печатает состояние карты, запросы к
API и ошибки консоли — инструмент для разбора «карта пустая» на проде.

## Разработка до запуска: прод как стенд

Пока у сервиса нет пользователей, прод одновременно является стендом, и это ускоряет разработку:
не нужно держать вторую среду, а проверка идёт на реальных данных и реальном окружении (Caddy, TLS,
2 vCPU). Правила, которые делают такой режим безопасным:

- **Бэкап перед каждым деплоем** — `update.sh` снимает дамп до пересборки, откат данных возможен
  в любой момент.
- **Репетиция миграции на копии прод-дампа** — перед накатом схемы: снять дамп, развернуть в отдельную
  базу, прогнать `alembic upgrade head`, сверить контрольные числа. На Этапе 8 это ловит ошибки
  дешевле, чем прод.
- **Релизы тегами** — откат кода = развёртывание архива предыдущего тега.
- **Проверка после деплоя** — `update.sh` проверяет `/healthz` и `/readyz`, плюс браузерная проверка
  `frontend/scripts/prod-smoke.mjs` (карта, ячейки, клик по ячейке) и точечные `curl` к изменённым
  эндпоинтам.
- **Мониторинг** — cron каждые 5 минут; при поломке это видно в `/var/log/geopuls/monitor.log`
  (вебхук для алертов пока не задан — см. раздел «Мониторинг»).

Чего на боевом боксе не делаем:

- **Нагрузочные прогоны с высокой конкурентностью**: 2 vCPU обслуживают и сайт, и прогон. Ориентир —
  не выше 6 одновременных запросов (как в `docs/acceptance/2026-09-28-load.md`), иначе стенд
  становится недоступен для нас же.
- **Правки данных вручную** (SQL, импорт с экспериментальными правилами) без свежего дампа: это
  единственная копия данных, которой мы располагаем.
- **Долгая отладка фронтенда на проде**: итерации удобнее локально (`npm run dev`, hot reload), на прод
  уезжают законченные шаги.

После запуска (появление пользователей) эти правила меняются: нужна отдельная среда для проверок,
а прод становится тем, что нельзя ломать.

## Редактор на сервере: code-server (30.09.2026)

Разработку можно продолжать не только со своей машины: на сервере стоит **code-server** (VS Code в
браузере) с расширением Cline, нашими инструментами и рабочей копией репозитория.

- Адрес: `https://code.<DOMAIN>/` (для прода — `https://code.201.34.158.13.sslip.io`), вход по паролю
  code-server. TLS выпускает тот же Caddy; наружу порт редактора (8080) не открыт — редактор слушает
  адрес хоста в сети проекта (шлюз, в примере `172.18.0.1:8080`), а Caddy из контейнера ходит к нему по
  переменной `CODE_UPSTREAM` (`infra/Caddyfile`, `docker-compose.yml`). `host.docker.internal` для этого
  не подходит: в этом Docker он указывает на docker0 (`172.17.0.1`), где редактор не слушает, — отсюда
  был 502 при первой попытке.
- Если сеть проекта пересоздана (например, `docker compose down` с удалением сети), её шлюз может
  смениться: повторный `bash infra/ops/install-code-server.sh` пересчитает адрес, а новое значение нужно
  вписать в `CODE_UPSTREAM` файла `/opt/geopuls/.env` и применить —
  `cd /opt/geopuls && docker compose --profile prod up -d caddy`.
- Рабочая копия: `/root/work/Geopuls` — настоящий git-репозиторий. Это **не** `/opt/geopuls`: там лежит
  распакованный архив прода без истории, и его перезаписывает каждый деплой.
- Инструменты на сервере: Node.js (фронтенд), `uv` (pytest и ruff в окружении проекта), PowerShell
  (наши `tools/*.ps1`), git, docker. Расширения: Cline, Python, Ruff, ESLint.
- Установка и обновление — скриптами из репозитория: `bash infra/ops/install-code-server.sh`,
  `bash infra/ops/install-dev-tools.sh`.
- Деплой из редактора: `bash infra/ops/deploy-from-worktree.sh` — тот же путь, что у `tools/deploy.ps1`
  (бэкап → архив HEAD → `update.sh` → проверка), но без заливки архива с ноутбука. Коммит при этом
  остаётся только на сервере, пока не сделан `git push`.
- Память редактора ограничена (`MemoryMax=1500M` в systemd): на машине живут PostgreSQL и прод, и при
  нехватке памяти ядро должно зарезать редактор, а не контейнеры. Тяжёлые прогоны (импорт PBF,
  нагрузочные тесты) не стоит запускать одновременно с прод-нагрузкой.
- Push в GitHub с сервера идёт по deploy-ключу `/root/.ssh/id_ed25519_github`: публичная часть
  добавляется в настройках репозитория с галочкой «Allow write access». Без ключа не работает даже
  клон — репозиторий приватный.
- Что это меняет в безопасности: редактор — ещё одна дверь на ту же машину. Поэтому пароль длинный и
  случайный, порт наружу закрыт, TLS обязателен. Сменить пароль:
  `code-server --hash-password '<новый>'` → строка в `hashed-password` файла
  `/root/.config/code-server/config.yaml` → `systemctl restart code-server@root`.

## Безопасность

- **Вход по SSH — по ключу, пароль по сети выключен** (29.09.2026). Публичная часть `~/.ssh/id_ed25519`
  лежит в `/root/.ssh/authorized_keys`; настройка — в `/etc/ssh/sshd_config.d/00-geopuls.conf`:
  `PermitRootLogin prohibit-password`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`.
  Деплой и администрирование идут ключом: `tools/vps.py` и `tools/deploy.ps1` берут его из
  `~/.ssh/id_ed25519` (переопределение — `VPS_KEY`), `VPS_PASSWORD` остался резервным путём для
  серверов без ключа. Пароль root из выдачи провайдера, который ходил открытым текстом, теперь не
  работает по сети — но его стоит сменить в панели провайдера: он даёт доступ к консоли машины.
- Имя файла `00-geopuls.conf` выбрано намеренно: sshd берёт **первое** значение директивы, а
  `/etc/ssh/sshd_config.d/50-cloud-init.conf` из образа ставит `PasswordAuthentication yes`. С именем
  `99-…` наша настройка молча проигрывала (проверено на живом сервере). Поэтому проверять надо не
  запись в файле, а эффективное значение:
  `sshd -T -C user=root,host=localhost,addr=127.0.0.1 | grep -E 'password|permitrootlogin'`.
- Добавить ещё один ключ: `ssh root@<IP> "echo '<публичный ключ>' >> /root/.ssh/authorized_keys"`.
- Наружу открыты только 80/443; 5432/8000/3000 привязаны к `127.0.0.1`. Порты 465, 5060, 25, 53413,
  587, 389, 2525, 3389 закрыты на стороне провайдера — сервису они не нужны.
- `/opt/geopuls/.env` — права `600`; секреты и дампы не попадают в git (см. `.gitignore`).
- Firewall (`ufw`) на машине выключен, фильтрация — на стороне провайдера. Если включать `ufw`:
  разрешить 22, 80, 443 и 10050.
