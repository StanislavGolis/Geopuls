## 3. Решения по списку категорий

| Категория | Решение | Обоснование |
|---|---|---|
| `cafe` | Оставить как есть (`amenity=cafe`), 271 | Больше всего объектов с адресами (48%) и брендами среди общепита: сегмент размечен хорошо |
| `restaurant` | **Расширить**: `amenity=restaurant` + `amenity=fast_food` → 87 + 171 = **258** | `fast_food` — второй по величине тег общепита (171 против 87). Значения одного ключа взаимоисключающие, поэтому сумма точная. Для предпринимателя фастфуд — прямой конкурент ресторану |
| `bar` | Оставить (`amenity=bar`, `amenity=pub`), 64 | Проходит порог, но категория слабая — в UI помечается как «данные неполные», в приоритетах ниже |
| `pharmacy` | Оставить, 257 | 55% с адресом, 15 брендовых (сети) — можно показывать насыщенность сетями |
| `beauty` | Оставить (`shop=beauty` 92 + `shop=hairdresser` 250), 342 | Самый «малый бизнес» сегмент, покрытие отличное |
| `fitness` | **Уточнить**: `leisure=fitness_centre` + `leisure=sports_hall` → 33 + 13 = **46**; `leisure=fitness_station` (63) **не включать** | `fitness_station` — уличные тренажёры (не коммерческий объект), попадание дало бы мусор в карте конкурентов |
| `grocery` | Оставить (`shop=supermarket`+`convenience`+`grocery`), 596 | 248 объектов с брендом — лучшая категория для фичи «какие сети уже стоят» |
| `pickup_point` | Оставить (`shop=outpost` 482 + `amenity=parcel_locker` 19), 501 | Гипотеза ТЗ подтвердилась: это `shop=outpost`, а не «специальный» тег. 307 объектов с брендом (Ozon/Wildberries/СДЭК) |

**Итоговый список MVP — 8 категорий:** `cafe`, `restaurant` (+fast_food), `bar`, `pharmacy`,
`beauty`, `fitness` (+sports_hall), `grocery`, `pickup_point`. Уточнения добавляют 184 объекта,
то есть суммарно ≈ 2 335 объектов в bbox (точная цифра подтвердится при агрегации на Этапе 3).

## 5. Что осталось «вне категорий» (84.9% объектов с POI-тегами)

Большая часть — не конкуренты, а городская инфраструктура. Топ значений в bbox:

| Тег | Объектов | Что это |
|---|---|---|
| `amenity=parking` | 2 370 | парковки |
| `amenity=bench` | 1 015 | скамейки |
| `leisure=playground` | 780 | детские площадки |
| `amenity=waste_disposal` / `waste_basket` | 431 / 125 | мусорные контейнеры и урны |
| `amenity=atm` | 350 | банкоматы |
| `leisure=pitch` | 350 | спортплощадки |
| `amenity=drinking_water` | 227 | питьевые фонтанчики |
| `amenity=kindergarten` / `school` | 221 / 164 | детсады и школы |
| `leisure=park` | 217 | парки |

**Вывод:** доля «вне категорий» — не показатель качества, а следствие широкого определения POI.
Для оценки качества важнее два других числа: покрытие внутри категории (раздел 2) и полнота
адресов (раздел 6). Формулировка «84.9% объектов не попали в категории» **не должна**
использоваться в маркетинге как метрика покрытия.

## 6. Продуктовые выводы из данных

1. **Адреса заполнены не у всех** (32–61%): худшее покрытие — `pickup_point` (32%) и `beauty` (46%).
   В интерфейсе вместо пустого места в списке POI нужно писать «адрес не указан в OSM» — иначе
   пользователь решит, что список сломан.
2. **Бренды размечены там, где это сети**: `grocery` 248, `pickup_point` 307, `pharmacy` 15.
   Это готовая фича: «в этой ячейке 4 продуктовых, из них 3 федеральные сети» — прямой ответ на
   вопрос «с кем придётся конкурировать».
3. **20% объектов — полигоны (ways), а не точки**: `grocery` 120 из 596, `cafe` 20 из 271.
   Значит импортёр обязан читать геометрию ways (`locations=True`), иначе потеряется пятая часть
   данных, а это как раз крупные объекты (супермаркеты в зданиях).
4. **Мультикатегорийных объектов в Томске нет** (0): связь многие-ко-многим `poi_categories`
   сохраняем в модели, но в MVP она не влияет на вывод — упрощает агрегацию.
5. **Категории разного «веса»**: `grocery` (596) и `beauty` (342) против `bar` (64) и `fitness` (46).
   Для тепловой карты это означает разный масштаб — границы классов легенды должны считаться на
   бэкенде (`density_breaks` в API), иначе шкала будет либо «вся карта синяя», либо «вся бледная».

## 7. Ограничения измерений (что эти числа не означают)

- Полигональные POI-отношения (relations) в подсчёт по bbox не включены: по всему региону их 1 905,
  вклад в Томск не измерен. Ожидаемо он мал, но при импорте (Этап 2) их нужно обработать.
- Пересечения между разными ключами не измерялись: объект с `amenity=dentist` и `healthcare=dentist`
  посчитан дважды в разных строках. Для «кандидатов второй волны» это значит, что число оценочное.
- Разведка отвечает на вопрос «сколько размечено в OSM», а не «сколько организаций в городе».
  Реальная плотность выше; оценка неполноты — через сверку с ФНС/Росстатом (фаза 2).
- Сканирование идёт по всей выгрузке региона: ≈ 28 минут на проход при 1.7 ГБ RAM. Для регулярных
  прогонов нужно один раз вырезать bbox города в отдельный PBF (`osmium extract`) — это ускорит
  разведку и импорт на порядок. Задача добавлена в Этап 2.
