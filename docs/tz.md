# ГЕОПУЛЬС — техническое задание v0.2

> **Суть:** веб-сервис тепловых карт плотности организаций по городам России. Помогает
> предпринимателю малого бизнеса **визуально оценить конкурентную среду** и выбрать район для
> открытия точки — там, где гиганты (Яндекс Геоаналитика, 2ГИС Про) не работают или стоят неподъёмно.
>
> **Позиционирование:** «Карта пустых зон. Не прогноз трафика, а ответ на вопрос — где уже есть
> бизнес, а где его нет».
>
> **Формула:** открытые данные (OSM / Geofabrik, позже Росстат) → полная H3-сетка города →
> плотность POI по ячейкам → тепловая карта → список POI → решение о локации.

Статус документа: **согласуется**. Реализуемые решения зафиксированы в `docs/decisions/`.
Исходная версия ТЗ сохранена в `docs/archive/tz-v0.1.md`.

## Изменения относительно v0.1

| # | Было в v0.1 | Стало в v0.2 | Почему |
|---|---|---|---|
| 1 | Overpass API — единственный источник POI | **Geofabrik PBF/GPKG — основной источник**, Overpass API — резерв | Проверка 27.09.2026: `overpass-api.de` вернул `runtime error ... server is probably too busy`, зеркало `overpass.kumi.systems` — таймаут. | 2 | Тепловая карта по `poi_count` в H3-ячейке | Тепловая карта по **плотности** (POI/км²), `count` — в подписи | Площадь ячейки H3 res 9 различается до **1.99×** (min 0.0638 км², max 0.1271 км²), поэтому сырой `count` искажает карту до двух раз |
| 3 | Не сказано, какие ячейки попадают в БД | **Полная сетка города** (в т. ч. пустые ячейки, `count = 0`) | Продуктовое обещание — «карта пустых зон»; агрегация `GROUP BY` по POI пустые ячейки теряет |

| 7 | Юридика: только атрибуция ODbL | Добавлено разделение **Produced Work** (карта/тайлы) и **Derivative Database** (платный экспорт POI) | Экспорт POI — распространение производной базы: по ODbL её нужно отдавать под ODbL, без технических ограничений |
| 8 | Нет НФТ, тестов, CI, бэкапов, мониторинга, рисков | Добавлены разделы 8–10, 16–17 | Без них нельзя ни принять работу, ни эксплуатировать сервис |

## 1. Продукт и аудитория

| Сегмент | Что получает |
|---|---|
| **Предприниматель малого бизнеса** (B2C) | Визуальную оценку конкурентной среды: где в городе выбранная категория уже насыщена, а где нет; список POI по каждой зоне |
| **Города первой волны** | Томск, далее Барнаул, Кемерово, Тюмень — малые и средние города, где нет Яндекс Геоаналитики (16 миллионников) и недоступен по цене 2ГИС Про (от 36 000 ₽/мес) |

**Не для:** крупных сетей (свои аналитики), консалтинга (2ГИС Про), франшиз (отложено).

**Ключевой принцип честности:** сервис показывает *то, что размечено в OSM*, а не абсолютную
истину о рынке. Формулировки в интерфейсе, отчётах и маркетинге не должны обещать прогноз
трафика, оборота или доходности точки.

Правила отбора (те же, что в MVP, закреплены тестами): не берём городскую инфраструктуру (скамейки,
урны, площадки, светофоры); не дублируем слои — остановки, парковки, жильё, промзоны и пешеходные пути
измеряются площадью и километрами (ADR 0013); `healthcare=*` целиком не берём, только перечисленные
значения. Не заведены: сауны (36) и спортивные клубы (28) — ниже порога «категория не из десяти
объектов»; вузы — это точки притяжения (слой `anchors`), а не конкуренты.

Требования к маппингу:

1. **Разведка данных пройдена (Этап 0.5).** Пустых категорий нет: минимальная — `fitness` (33 объекта
   по `leisure=fitness_centre`, 46 после уточнения правил). Правила `restaurant` и `fitness` уточнены
   по факту данных: добавлен `amenity=fast_food` (171 объект), убран `leisure=sports_centre`+`sport=fitness`
   (дал 0 объектов) и добавлен `leisure=sports_hall`; `leisure=fitness_station` (63 уличных тренажёра)
   осознанно не включён. Кандидаты второй волны **реализованы 30.09.2026** (18 категорий вместо восьми) —
   правила и числа ниже.
2. **Объект может попадать в несколько категорий** (в OSM это норма): храним связь многие-ко-многим
   `poi_categories`, для тепловой карты категории считаем отдельно. В Томске таких объектов 0 —
   связь оставлена как задел под будущие категории.
3. **Агрегированные объекты:** POI бывают точками (node) и полигонами (way/relation, например здание
   с магазином). Геометрия нормализуется в точку: `POINT` как есть, полигон — центроид (для зданий —
   `ST_PointOnSurface`). Разведка показала, что ways — это **20% объектов** (`grocery` 120 из 596,
   `cafe` 20 из 271), поэтому чтение геометрии обязательно.
4. **Мало данных по адресам** (32–61% объектов с полным адресом, худшее — `pickup_point` 32%):
   в интерфейсе вместо пустого места пишем «адрес не указан в OSM», а доля адресов используется как
   индикатор зрелости данных ячейки.
5. Дубликаты (одинаковые названия и координаты в пределах ~30 м) помечаются флагом, но не удаляются
   автоматически: источник данных не должен «молча» терять объекты. Дедупликацию показываем в отчёте импорта.

### 2.3 Версионирование и обновление данных

- Каждая выгрузка фиксируется в таблице `import_runs`: источник, дата экстракта OSM (`osm_timestamp`),
  время старта/окончания, число объектов, статус.
- В интерфейсе и в API-ответах всегда показывается **дата данных** («Данные OSM на 27.09.2026»).
- Регламент обновления MVP: **раз в неделю** (Geofabrik обновляется ежедневно, недельный шаг — осознанный
  компромисс: меньше нагрузки и предсказуемые версии).
- Импорт идемпотентен: повторный запуск на той же выгрузке даёт тот же результат (тестируется в CI).
  Реализация — полная перезагрузка данных города в staging-таблицы с последующей атомарной заменой
  (объёмы малы, инкрементальные диффы OSM не нужны).
- Версия данных ведётся **по источнику**, а не по городу: у OSM это дата выгрузки, у растровых слоёв —
  эпоха снимка (например, GHSL R2023A). Интерфейс и экспорт перечисляют источники тех слоёв, которые
  видны на экране (ADR 0013); единая дата возможна только при единственном источнике.

### 2.4 Полнота данных — главное ограничение продукта

Полнота OSM зависит от активности сообщества: в спальных районах малых городов POI размечены
не полностью. Поэтому:

- в UI — постоянный дисклеймер «Источник: OpenStreetMap. Показано только то, что размечено
  сообществом; это не прогноз трафика»;
- рядом с картой — дата данных и **индикатор зрелости данных** (например, доля POI с заполненным
  адресом в ячейке);
- ссылка «Сообщить об объекте / исправить» → `https://www.openstreetmap.org/fixthemap` (заодно
  улучшает наш собственный датасет);
- в фазе 2 — сверка агрегатов с открытыми данными ФНС/Росстата («в OSM 40 объектов, по статистике
  зарегистрировано ~180») как честный индикатор неполноты.

## 3. Расчёты

### 3.1 MVP — только агрегация, без прогнозов

| Расчёт | Что делает | Формула/примечание |
|---|---|---|
| **Полная сетка города** | Все H3-ячейки res 9, покрывающие полигон города (включая пустые), плюс ячейки POI внутри полигона | Для Томска (177 км²) — **1 507 ячеек** res 9 и 217 res 8; 12 056 строк статистики для 8 категорий. Реализация: `geopuls.aggregate`, обоснование — `docs/decisions/0006-h3-aggregation.md` |
| **Количество POI** | Число объектов категории в ячейке | `count(*)`; POI фильтруются по полигону (`ST_Contains`), а не по bbox |
| **Плотность** | Плотность объектов категории в ячейке | `count / area_km2`, где `area_km2` — фактическая площадь ячейки (`h3.cell_area`); **основная метрика цвета** |
| **Тепловая карта** | Цвет по плотности: мало → много | Границы классов (`density_breaks`) считаются на бэкенде квантильно; нулевые ячейки — отдельный цвет |
| **Список POI** | Название, адрес (если есть в OSM), бренд | По клику на ячейку |

Метрики H3 res 9 (официальная документация): средняя длина ребра — **0.200786 км**, средняя площадь —
**0.105332513 км²**, min/max площадь — 0.063780227 / 0.127090737 км² (отношение **1.99**).
Именно из-за этого разброса цвет считается по плотности, а не по количеству.

### 3.2 Слои (следующий шаг) и фаза 2 — индекс привлекательности

Между MVP и индексом появляется промежуточный шаг: **описательные слои** (ADR 0013) — конкурентная
среда, население, жильё, работа, транспорт, парковки. Они поставляют входные данные для компонентов
ниже, но сами не считают никаких весов и баллов: «здесь жильё и остановка, кафе нет» — факт,
«открывайте здесь» — уже рекомендация, и она остаётся вне продукта (раздел 12).

| Компонент | Метод | Источник | Когда |
|---|---|---|---|
| Конкурентная среда | Число POI той же категории в радиусе 500 м (`ST_DWithin`, точный радиус — не приближение по сетке) | OSM | фаза 2 — **сделано 30.09.2026** |
| Плотность инфраструктуры | Общее число POI всех типов в радиусе 500 м | OSM | фаза 2 — **сделано 30.09.2026** |
| Прокси трафика | Близость к объектам слоя `transport` и слоя `anchors` (ТЦ, вузы, больницы, вокзалы, рынки) | OSM, слои Этапа 9 | слои — Этап 9, расчёт радиуса — **сделано 30.09.2026** |
| Демография | Плотность населения по ячейке (сетка 100 м, агрегация в H3) | **GHSL `GHS-POP`** (ADR 0013); Росстат — вне проекта | Этап 10 |
| Обеспеченность | Число объектов категории на 1000 жителей, сравнение со средним по городу | композитный слой `provision` | Этап 10 |
| Индекс привлекательности | Взвешенная сумма компонентов (0–100) | Huff model, AHP | фаза 2, отдельное решение и юридическая проверка |

**Важно:** модель Хаффа — классическая гравитационная модель в ритейле: вероятность посещения точки
пропорциональна её привлекательности и обратно пропорциональна расстоянию. В MVP **не используется** —
только плотность. Радиус 500 м в фазе 2 считается через PostGIS `ST_DWithin`, а не через `grid_disk`
H3: приближение по сетке даёт ошибку до полутора ячеек (≈ 300 м) на границах.

Реализовано (30.09.2026): `GET /api/v1/around?city=tomsk&lat=…&lon=…&category=cafe&radius_m=500` — по
каждому слою число объектов в круге и ближайший с расстоянием и именем; радиус от 100 до 2000 м; ETag по
версии данных. Доли площади и проценты в круге не считаются и в ответе не появляются. В интерфейсе это
вкладка «Инструменты» → «Радиус вокруг точки»: клик по карте ставит точку, круг рисуется тем же радиусом,
состояние — в ссылке (`docs/design/design.md` §4.0 и §4.14,
`docs/plan/2026-09-30-development-plan.md` §4.1).

### 4.1 Экран «Карта»

Экран разделён на вкладки-сцены: «Конкуренты», «Инфраструктура», «Инструменты», «Город» (ADR 0016,
дизайн-спека §4.0). Вкладка определяет, какой слой красит карту, что выбирается в панели сцены и какая
панель данных открыта. Состояние сцены живёт в ссылке (`tab` — только для неосновных вкладок); при чтении
вкладка выводится из состояния, поэтому ссылки, разошедшиеся до вкладок (`profile=1`, `compare=…`,
`around=…`, `base=residential`), открывают то же, что и раньше.

```
┌──────────────────────────────────────────────────┐
│ ГЕОПУЛЬС   [Томск ▾]  [Кафе ▾]        [⤴ Поделиться] │
```

|---|---|

| Сводка по зонам | Топ-5 зон по значению слоя и распределение по классам плотности (отдельно «пусто» и «нет данных»); считается по загруженной сетке (дизайн-спека §4.15) |

### 4.3 Обязательные требования к UX

1. **Mobile-first.** Целевой пользователь откроет сервис с телефона: тач-жесты карты, панель списка POI
   снизу (bottom sheet), шкала легенды помещается на экран 360 px, тап-таргеты ≥ 44 px.
2. **Разрешение H3 зависит от зума:** обзор города — res 8, детальный вид — res 9. Иначе на обзорном
   зуме рисуются тысячи гексагонов и слой становится визуальным шумом.
3. **Состояния:** skeleton при загрузке, пустое состояние («в этом городе нет размеченных объектов
   категории»), понятная ошибка с кнопкой «повторить», работа при недоступном API (последние
   успешные данные + баннер «нет связи»).
4. **Shareable URL** без регистрации: состояние полностью описывается query-параметрами
   (`?city=tomsk&category=cafe&res=9&cell=…`).
5. **Дисклеймер о данных** — видимый, не спрятанный в тултип: «Только объекты, размеченные в OSM.
   Это не прогноз трафика и не оценка доходности».
6. **Экспорт текущего вида** (PNG карты и CSV ячеек) — бесплатно; это драйвер сарафанного радио.

### 5.1 Стек и версии

| Слой | Решение | Версия / примечание |
|---|---|---|
| Источник данных | Geofabrik Siberian FD PBF, Overpass API (резерв) | PBF ≈ 557 МБ, обновляется ежедневно |
| Импорт | Python 3.14, `pyogrio` (GPKG) / `pyosmium` (PBF), `httpx`, `orjson` | Колёса под 3.14 проверены: `h3 4.5.0`, `shapely 2.1.2`, `pyproj 3.8.0`, `pyogrio 0.13.0`, `geopandas 1.1.4`, `numpy 2.5.3`, `pandas 3.0.6`. **`fiona` не используем** — колёс под 3.14 нет, geopandas 1.x работает через `pyogrio` |
| Хранение | PostgreSQL **17** + PostGIS **3.5** (`postgis/postgis:17-3.5`) | Точный радиус, клип по полигону, `GEOGRAPHY(POINT, 4326)` |
| Агрегация | `h3` (ядро H3 **4.5.0**), resolution 9 (детально) / 8 (обзор) | H3-индекс вычисляется в Python при импорте, хранится как `bigint`; расширение `pg_h3` не требуется |

| Фронтенд | Next.js **16.x** + TypeScript, MapLibre GL JS **6.x**, `h3-js` **4.5** | Ядро H3 на фронте и бэке обязано совпадать (4.5); 3.x и 4.x несовместимы |
| Подложка карты | OpenFreeMap (MVP) → self-host PMTiles (Protomaps) в прод | См. 5.2 и `docs/decisions/0002-basemap.md` |
| Инфраструктура | Docker Compose, Caddy (авто-TLS), VPS | Бэкапы `pg_dump` + проверка восстановления |
| CI/CD | GitHub Actions: `ruff` + `pytest` (backend), `tsc` + `next build` (frontend) | См. `.github/workflows/ci.yml` |

### 5.2 Подложка карты — обязательное решение

Политика OSMF по тайлам `tile.openstreetmap.org`: доступ best-effort **без SLA**, запрещены prefetch,
offline и bulk-загрузка, а коммерческим сервисам прямо рекомендуется помнить, что доступ может быть
отозван в любой момент. Для платного продукта это неприемлемо.

| Вариант | Коммерческое использование | Ключ/лимиты | Роль |
|---|---|---|---|
| **OpenFreeMap** | Разрешено | Ключ не нужен, лимитов просмотров нет, SLA нет | MVP и первая продакшн-версия |
| **Protomaps PMTiles (self-host)** | Да, «Produced Work» ODbL, требуется атрибуция OSM | Нет | Прод с ростом трафика: `pmtiles extract` даёт вырезку по региону (планета целиком ≈ 120 ГБ z0–15) |
| MapTiler / Stadia Maps | По тарифу | Ключ + лимиты | Запасной вариант при требовании SLA |
| `tile.openstreetmap.org` | Риск блокировки | — | Только локальная разработка, не в прод |

Атрибуция обязательна: «© OpenStreetMap contributors» + атрибуция подложки (для OpenFreeMap —
«OpenFreeMap © OpenMapTiles Data from OpenStreetMap»; MapLibre добавляет её автоматически).
Та же атрибуция — в экспортируемых отчётах и CSV.

### 5.3 Кэширование

Данные меняются раз в неделю, поэтому:

- агрегаты по городу и категории отдаются как `GeoJSON`/JSON с `ETag` и `Cache-Control: public, max-age=3600`;
- допустимо предпосчитать статические JSON-файлы (`/static/cells/{city}/{category}/{res}.json`) и отдавать
  их через reverse-proxy/CDN — для MVP это дешевле и быстрее прямых запросов в БД;
- ключ кэша включает `data_version` (дата выгрузки OSM), чтобы обновление данных инвалидировало кэш.

## 6. Модель данных

```

  id            serial pk
  slug          text unique             -- 'cafe', 'pharmacy', ...
  name_ru       text                    -- «Кофейни и кафе»
  osm_tags      jsonb                   -- [{"key":"amenity","value":"cafe"}]
  color         text                    -- цвет для легенды
  is_active     boolean default true
  sort_order    int

  id            serial pk
  slug          text unique             -- 'tomsk'
  name          text                    -- 'Томск'
  region        text
  osm_relation_id bigint                -- relation городского округа в OSM
  boundary      geography(Polygon,4326) -- полигон города (не bbox!)
  bbox          geography(Polygon,4326) -- прямоугольник-префильтр
  center        geography(Point,4326)
  h3_res        smallint default 9
  population    int null
  timezone      text default 'Asia/Tomsk'
  is_active     boolean default true

pois
  id            bigserial pk
  osm_type      text                    -- 'node' | 'way' | 'relation'
  osm_id        bigint
  name          text null
  brand         text null
  addr_street   text null
  addr_housenumber text null
  location      geography(Point,4326)
  h3_r9         bigint                  -- индекс ячейки res 9, вычисляется при импорте
  h3_r8         bigint
  tags          jsonb                   -- полный набор тегов OSM
  is_active     boolean default true    -- мягкое удаление (объект исчез из OSM)

  source        text                    -- 'geofabrik' | 'overpass' | 'overture'
  osm_version   int null
  updated_at    timestamptz
  unique (osm_type, osm_id)
  index (h3_r9), index (h3_r8), gist (location)

poi_categories              -- многие-ко-многим: объект может быть в нескольких категориях
  poi_id        bigint fk -> pois
  category_id   int fk -> categories
  primary key (poi_id, category_id)

city_cells                  -- ПОЛНАЯ сетка города, включая пустые ячейки
  city_id       int fk -> cities
  h3_index      bigint
  resolution    smallint
  centroid      geography(Point,4326)
  area_km2      double precision        -- фактическая площадь ячейки
  primary key (city_id, resolution, h3_index)

cell_stats                  -- агрегаты по категориям
  city_id       int fk -> cities
  h3_index      bigint
  resolution    smallint
  category_id   int fk -> categories
  poi_count     int                     -- число POI
  density       double precision        -- poi_count / area_km2  (метрика цвета)
  has_address_ratio double precision null -- доля POI с адресом (индикатор полноты)
  primary key (city_id, resolution, h3_index, category_id)

import_runs
  id            bigserial pk
  source        text                    -- 'geofabrik' | 'overpass'
  source_url    text
  osm_timestamp timestamptz             -- «данные на <дата>»
  started_at    timestamptz
  finished_at   timestamptz null
  status        text                    -- 'running' | 'ok' | 'failed'
  city_id       int fk -> cities null   -- null = импорт всего региона
  pois_upserted int
  cells_written int
  error         text null

data_versions               -- версия данных для кэша и UI
  id            serial pk
  version       text                    -- '2026-09-27'
  created_at    timestamptz
```

Замечания к модели:

1. `lat/lon` **не хранятся** отдельно — только `location`, иначе появляется второй источник истины
   (расхождение при обновлении). При необходимости координаты достаются из `location`.
2. `h3_r9`/`h3_r8` заполняются при импорте (Python, `h3-py`): агрегация становится обычным
   `GROUP BY`, без пространственных джойнов.
3. `city_cells` заполняется по полигону города, а не по bbox: bbox затягивает пригороды и дачи.
   Пустых ячеек в тепловой карте быть не должно — именно они и есть продукт.
4. `poi_count` и `density` лежат рядом: `count` нужен для подписи и сортировки, `density` — для цвета.

**Реализация (Этап 1, 28.09.2026):** модели — `backend/src/geopuls/models/`, миграции —
`backend/migrations/` (0001 — расширение PostGIS, 0002 — схема), сид — `python -m geopuls.seed`.
Отличия от проектной схемы выше: добавлены `cities.boundary_source` (происхождение границы),
`cities.h3_res`, `cities.timezone`, `pois.h3_r8`, `pois.has_address`; отдельные `lat`/`lon` не хранятся —
только `location`. Граница города берётся из Nominatim (`docs/decisions/0004-city-boundary.md`),
в тестах используется сохранённая фикстура, CI не ходит в сеть. Соответствие моделей и миграций
проверяется в CI шагом `alembic check` — расхождение ломает сборку.

### 6.1 Слои, метрики и источники (проект, Этап 8)

Проект схемы под мультислойность — ADR 0013. Смысл: категория перестаёт быть верхним уровнем, его
занимает слой, а у значения метрики появляется тип.

```
layers                          -- слой: продуктовая единица (конкуренты, население, транспорт, ...)
  id            serial pk
  slug          text unique     -- 'competitors', 'population', 'transport', ...
  name_ru       text
  kind          text            -- 'osm' | 'raster' | 'composite'
  metric_kind   text            -- count | density | area_share | people | people_density | ratio | presence
  unit          text            -- 'POI/км²', 'чел/км²', 'доля площади'
  scale         text            -- 'quantile' | 'linear' | 'log' (как считать границы классов)
  color         text            -- базовый цвет слоя (легенда, наложения)
  can_be_base   boolean         -- может ли слой красить карту (только один базовый за раз)
  dataset_id    int fk -> datasets
  sort_order    int
  is_active     boolean default true

datasets                        -- источник данных и его условия (атрибуция, лицензия, версия)
  id, slug, title, license, license_url, attribution_text, citation, source_url,
  data_version  text            -- у OSM '2026-09-27', у GHSL '2020 (R2023A)'
  updated_at    timestamptz

cell_metrics                    -- одна таблица значений вместо таблицы на каждый слой
  city_id       int  fk -> cities
  layer_id      int  fk -> layers
  category_id   int  null fk -> categories      -- вариант внутри слоя
  resolution    smallint
  h3_index      bigint
  value         double precision                -- смысл задаётся слоем
  value_kind    text                            -- копия metric_kind, чтобы значение читалось без join
  dataset_id    int  fk -> datasets
  data_version  text
  computed_at   timestamptz
  primary key (city_id, layer_id, coalesce(category_id, 0), resolution, h3_index, data_version)

categories
  + layer_id    int  fk -> layers   -- вариант внутри слоя; у слоя «Конкуренты» — прежние 8 категорий
```

Замечания к проекту:

1. `metric_kind` — часть контракта: одна и та же шкала неприменима к «штукам на км²» и «человекам на
   км²», поэтому тип значения определяет формат, легенду, единицы и округление.
2. `data_version` входит в ключ: снимки агрегата не затираются, и через полгода появится динамика
   («открылось N, закрылось M») без отдельной миграции задним числом.
3. `cell_stats` переносится в `cell_metrics`; на переходный период API поддерживает оба вида чтения,
   чтобы фронтенд, E2E и экспорт не падали в один шаг.
4. Колонка `cities.population` (уже есть, не используется) остаётся справочной — население города из
   слоя не вычисляется.
5. Растровые слои попадают в `cell_metrics` только после офлайн-агрегации в H3 (area-weighted), а не
   читаются из растра на каждый запрос: время ответа API не должно зависеть от размера растра.

## 7. API

Базовый префикс `/api/v1`. Формат ошибок — RFC 9457 (`application/problem+json`).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/meta/cities` | список городов (slug, название, центр, bbox, площадь, `data_version`) |
| GET | `/api/v1/meta/categories` | категории (slug, название, цвет, число активных POI) |
| GET | `/api/v1/cells` | тепловой слой города по категории (GeoJSON) |
| GET | `/api/v1/pois` | объекты внутри ячейки H3 |
| GET | `/healthz` | живость процесса (без обращения к БД) |
| GET | `/readyz` | готовность (проверка `SELECT 1` в БД) |
| GET | `/version` | версия приложения, коммит, версия ядра H3, версия Python |

Параметры запросов:

| Endpoint | Параметры |
|---|---|
| `/cells` | `city` (обязательный), `category` (обязательный), `res` = 8 \| 9 (по умолчанию 9), `bbox` = `min_lon,min_lat,max_lon,max_lat` (для загрузки только видимой области) |
| `/pois` | `city` (обязательный), `cell` (H3-индекс, обязательный), `res` (по умолчанию 9), `category` (фильтр), `limit` ≤ 500, `offset` |

Коды ответов:

| Код | Когда | Тело |
|---|---|---|
| 200 | данные есть | GeoJSON / JSON со всеми `meta`-полями |
| 304 | `If-None-Match` совпал с `ETag` | пустое (данные не менялись) |
| 400 | некорректный `bbox` или H3-индекс | problem+json |
| 404 | город, категория не найдены; ячейка вне сетки города | problem+json |
| 422 | неверные параметры (например `res=7`) | problem+json со списком ошибок |
| 503 | сетка города ещё не собрана (не выполнен импорт/агрегация) либо нет соединения с БД | problem+json |

Кэширование: каждый ответ с данными содержит `ETag` (по городу, категории, разрешению, версии
данных и фильтру) и `Cache-Control: public, max-age=3600` — данные меняются раз в неделю, поэтому
повторные запросы браузера отдают 304 без обращения к БД. Ответы сжимаются gzip на уровне приложения
(не только на reverse-proxy).

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "id": "890b80db643ffff",
      "properties": {"h3": "890b80db643ffff", "count": 2, "density": 17.1, "has_address_ratio": 0.5},
      "geometry": {"type": "Polygon", "coordinates": [[[85.02, 56.51], "..."]]}
    }
  ],
  "meta": {
    "city": "tomsk",
    "category": "cafe",
    "res": 9,
    "data_version": "2026-09-27",
    "updated_at": "2026-09-28T12:39:25Z",
    "cell_count": 1507,
    "non_empty_count": 130,
    "poi_count": 248,
    "max_density": 76.9,
    "density_breaks": [0, 25.6, 42.7, 59.8, 76.9]
  }
}
```

`id` фичи — текстовый H3-индекс: фронтенд может передать его в `/api/v1/pois?cell=…` и использовать
с `h3-js` без преобразований. `density_breaks` (границы классов легенды) считаются на бэкенде —
фронтенд только раскрашивает, чтобы шкала была одинаковой в web-, PNG- и PDF-представлениях.
Порядок координат — GeoJSON (`[lon, lat]`).

Требования к API:

1. `ETag` + `Cache-Control` на `/cells` и `/pois`; тело ответа сжимается (gzip/brotli на proxy).
2. Ограничение размера ответа: при `res=9` и обзоре всего города допускается серверная прореживание
   (отдавать `res=8` вместо `res=9`, если клиент этого ещё не сделал).
3. `meta.data_version` и `meta.updated_at` обязательны в каждом ответе с данными — UI показывает дату.
4. Версионирование: `/api/v1`, ломающие изменения — только в `/api/v2`.

### 7.1 API слоёв (проект, Этап 8)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/layers` | реестр слоёв: slug, название, вид, метрика, единица, цвет, `can_be_base`, источник и его версия |
| GET | `/api/v1/layers/{slug}/cells` | значения одного слоя по сетке города (параметры как у `/cells`) |
| GET | `/api/v1/map` | карта целиком: базовый слой плюс дополнительные слои (не больше шести) одним колоночным ответом |
| GET | `/api/v1/cells/{h3}` | профиль ячейки: значения всех слоёв плюс производные описательные показатели |
| GET | `/api/v1/meta/cities/{slug}/profile` | профиль города: охват сетки, категории конкурентов, все слои и источники одним ответом (план развития, этап 1) |
| GET | `/api/v1/cells` | прежний контракт; параметр `category` трактуется как `layer=competitors` |

Несколько слоёв отдаются одним колоночным ответом (`/api/v1/map`): геометрия ячеек — **один раз**,
значения слоёв — массивами, выровненными по порядку ячеек. Сетку задаёт базовый слой: он красит
заливку, и именно его ячейки (включая пустые) образуют «карту пустых зон». Дополнительные слои на
карту не рисуются: их значения читаются по той же ячейке в карточке ячейки (уточнено 30.09.2026).

Реализовано 29.09.2026 (ADR 0013, шаг 4). Замер на Томске (1 507 ячеек res 9): один слой — 281 КБ JSON
(51,3 КБ gzip), три слоя — 294 КБ JSON (51,6 КБ gzip): добавление слоя стоит колонки чисел, а не ещё
одной копии геометрии. Числа сверяются с `/cells` тестом `backend/tests/test_map_api.py`.

```json
{
  "type": "LayerGrid",
  "cells": {"h3": ["890b80db643ffff", "..."], "geometry": [[[85.02, 56.51], "...", [85.02, 56.51]], "..."]},
  "layers": [
    {"slug": "competitors", "category": "cafe", "role": "base", "metric_kind": "density",
     "unit": "POI/км²", "values": [17.1, "..."], "extras": {"count": [2, "..."]},
     "breaks": [0, 25.6, 42.7, 59.8, 76.9], "non_empty_count": 130},
    {"slug": "population", "category": null, "role": "overlay", "metric_kind": "people_density",
     "unit": "чел/км²", "values": [3120, "..."], "breaks": ["..."], "covered_count": 1507}
  ],
  "meta": {
    "city": "tomsk", "res": 9, "cell_count": 1507, "base": "competitors:cafe", "overlays": ["population"],
    "data_version": "2026-09-27",
    "sources": [
      {"slug": "osm", "data_version": "2026-09-27"}
    ]
  }
}
```

Значение `null` в массиве `values` означает «у слоя нет значения для этой ячейки» (слой собран не по
всей сетке) — это не то же самое, что `0` («объектов нет»). Различать их обязательно: иначе
недособранный слой выглядит как пустой город.

Требования к слоям в API:

1. Размер: три слоя на город — ориентир не более ~100 КБ gzip (сегодня один слой — 57 КБ gzip при
   485 КБ JSON). `ETag` считается по набору слоёв, разрешению и версиям источников.
2. Заливку задаёт только один слой в ответе (`can_be_base`); остальные слои — дополнительные: их
   значения читаются по ячейке, а не рисуются поверх заливки. Проверяется на уровне API: два базовых
   слоя в одном запросе — 400, больше шести слоёв — 400 (это уже технический лимит размера ответа).
3. `meta.sources` обязателен всегда: интерфейс и экспорт показывают источники и версии именно тех
   слоёв, которые видит пользователь, а не одну дату на всё.

## 9. Инфраструктура и эксплуатация

### 9.1 Развёртывание

- `docker compose`: `db` (PostgreSQL 17 + PostGIS 3.5), `api` (FastAPI/Uvicorn), `web` (Next.js standalone),
  `caddy` (TLS + reverse-proxy, профиль `prod`), позже `scheduler` (импорт/агрегация по расписанию).
- Весь стек в контейнерах одной командой: `pwsh -File tools/docker-up.ps1` (сборка → запуск → ожидание
  health), остановка — `pwsh -File tools/docker-down.ps1`. Контейнер API при старте применяет миграции
  Alembic и идемпотентно сидирует справочник категорий (`backend/docker-entrypoint.sh`), поэтому свежий
  том готов к работе сразу; город, POI и агрегация загружаются отдельными командами
  (`docker compose run --rm api python -m …`) — выгрузка OSM в образ не входит.
- Порядок запуска задан healthcheck'ами: `db → api → web`. Прод-профиль добавляет Caddy с авто-TLS.
- Локальная разработка: `pwsh -File tools/dev-up.ps1` (БД в Docker, API и фронтенд нативно).
- Прод: один VPS; Caddy получает TLS автоматически (Let's Encrypt); фронтенд — статика/Next standalone.
  Развёрнут 28.09.2026: https://201.34.158.13.sslip.io (Ubuntu 26.04, 2 vCPU, 3.9 ГБ). Наружу открыты
  только 80/443, остальные сервисы слушают `127.0.0.1`. Полная инструкция — `docs/deploy.md`,
  скрипты — `infra/ops/`.
- Резервные копии: `tools/db-backup.ps1` (pg_dump в `data/backups`, ротация 14 дней) и
  `tools/db-restore.ps1` — восстановление в отдельную базу со **сверкой числа строк**; проверка
  восстановления обязательна перед релизом и раз в квартал (§9.1, отчёт —
  `docs/acceptance/2026-09-28-backup.md`).
- Секреты — только через env/секреты CI, файл `.env` в git не попадает (`.env.example` — в git).

### 9.2 Импорт и расписание

| Шаг | Что делает |
|---|---|
| 1. Скачивание | `siberian-fed-district-<дата>.osm.pbf` (или GPKG) → `data/raw/`, фиксируется дата и контрольная сумма (`tools/fetch-osm-extract.ps1`) |
| 2. Сканирование | один проход по выгрузке: объекты с POI-тегами внутри объединения bbox **всех активных городов** → файл-кандидатов `*.poi-candidates.jsonl`, отчёт по категориям |
| 3. Запись | батчевый upsert в `pois` и `poi_categories` одной транзакцией |
| 4. Мягкое удаление | объекты, не встреченные в выгрузке, помечаются `is_active = false` по «водяному знаку» времени БД (`clock_timestamp()`) — см. `docs/decisions/0005-poi-import.md` |
| 5. Агрегация | пересборка `city_cells` (полная сетка города) и `cell_stats` (количество, плотность, доля адресов) — см. `docs/decisions/0006-h3-aggregation.md` |
| 6. Публикация | новая запись `data_versions`, обновление `import_runs` (статус, объёмы, дата данных) |
| 7. Отчёт | логи импорта, уведомление при падении (алерт) |

Команды:

```bash
# полный цикл: сканирование выгрузки + запись в БД
uv run python -m geopuls.importers.poi --pbf data/raw/siberian-fed-district-260927.osm.pbf
# только сканирование (файл-кандидатов) с отчётом
uv run python -m geopuls.importers.poi --pbf data/raw/... --dry-run
# повторная запись из готового файла-кандидатов (секунды)
uv run python -m geopuls.importers.poi --from-dump data/raw/....poi-candidates.jsonl

# агрегация H3: полная сетка города и статистика по ячейкам (после импорта)
uv run python -m geopuls.aggregate --city tomsk
```

Одна команда на город (справочники → импорт POI → агрегация): `python -m geopuls.refresh --city tomsk
--pbf <выгрузка>.pbf` — обёртка `tools/refresh-data.ps1`, в контейнерном стеке
`docker compose run --rm api python -m geopuls.refresh …`. Повторный запуск идемпотентен (проверяется
тестом `backend/tests/test_refresh.py`), ненулевой код возврата — сигнал для уведомления (§9.3).

Расписание MVP: еженедельно (ночной запуск) — cron или systemd-timer на VPS, вызывающий `geopuls.refresh`.
Замер на проде (Томск, выгрузка Сибирского ФО 557 МБ, 2 vCPU): скачивание ≈ 2 мин, скан ≈ 40 мин,
агрегация 0.2 с; пик памяти контейнера импорта 1.78 ГиБ — окно 02:30 закрывается до бэкапа в 03:20.

### 9.3 Наблюдаемость

- Структурные логи (JSON) приложения и импортёра; уровень — из env.
- `/healthz` (процесс) и `/readyz` (БД) для внешней проверки; uptime-мониторинг + алерт.
- Отчёты об ошибках фронтенда (self-hosted Sentry или аналог) — начиная с Этапа 5.
- Алерты: импорт упал, данные старше 14 дней, `/readyz` недоступен 5 минут, диск/память > 85%.

### 9.4 CI/CD (`.github/workflows/ci.yml`)

| Job | Шаги |
|---|---|
| `backend` | `uv sync --locked`, `ruff check`, `ruff format --check`, `pytest` (с сервисом PostGIS в CI) |
| `frontend` | `npm ci`, `npm run typecheck`, `npm run test`, `npm run build`, проверка воркера MapLibre в `public/` |
| `compose` | `docker compose config` — валидация конфигурации |
| `images` | `docker compose build api web` — сборка образов (поломка Dockerfile видна в CI, а не при деплое) |

Деплой MVP — вручную, от тега: релиз помечается аннотированным тегом (`git tag -a vX.Y.Z`), на сервер
уезжает архив этого тега (`git archive <тег>`), развёртывание выполняет `infra/ops/update.sh`
(бэкап → сборка образов на сервере → перезапуск → проверка). Реестра образов нет, поэтому `docker
compose pull` в процессе не участвует: образы собираются на сервере из исходников коммита.
Автоматизация CD — после запуска; пошаговая инструкция и откат — `docs/deploy.md`.

Текущий релиз: **`v0.1.0-mvp`** — развёрнут на https://201.34.158.13.sslip.io; состояние кода,
данных и проверок описано в `docs/acceptance/`. Какой коммит реально работает, видно в `/version`:

## 12. Что НЕ входит в MVP

- Индекс привлекательности и любые «рекомендации, где открывать» (юридический и репутационный риск).
  Граница проходит между описанием и предписанием: факты и производные описательные показатели
  (население в ячейке, число остановок, «кафе на 1000 жителей») продукт показывает, сводный балл,
  рейтинг зон и совет «открывайте здесь» — нет. Уточнение — ADR 0013, разделы 3.2 и 7.1.
- Прогноз трафика, оборота, окупаемости
- Демография Росстата и кадастровая стоимость (Росреестр). Исключение сделано для населения из
  открытой сетки GHSL: это описательный слой Этапа 10 с указанием источника и эпохи данных (ADR 0013)
- Дополнительные слои (жильё, работа, транспорт, парковки, население) — после MVP, Этапы 8–11:
  они описательные и индекса не образуют
- Мультигородность (только Томск; архитектура к ней готова — `city_id` везде)
- Аккаунты пользователей, личный кабинет, история поиска
- Монетизация: платежи, отчёты, подписка
- Overture Maps как источник: в MVP не входит. Разведка 30.09.2026 показала, что по семи из восьми
  наших категорий он беднее OSM в Томске, а его темы `base` и `buildings` — это сам OSM под ODbL
  (`docs/recon/2026-09-30-overture-maps.md`). Условия подключения темы `places`, если продукт решит,
  описаны там же
- Мобильное приложение

## 13. Монетизация (после MVP)

| Уровень | Цена | Что входит |
|---|---|---|
| **Бесплатно** | 0 ₽ | Тепловая карта, 1 категория, экспорт текущего вида (PNG/CSV), shareable-ссылка |
| **Разовый отчёт** | 490–990 ₽ | Все категории, детальный список POI по зоне, PDF-отчёт с картой и легендой |
| **Подписка** | 490 ₽/мес | Всё + новые города + обновления данных |

**Логика:** предприниматель в Томске не заплатит 60 000 ₽ (как 2ГИС), но заплатит 500 ₽ за «покажи,
где конкуренты».

**Предусловия монетизации (без них продавать нельзя):**

1. юридическое лицо или самозанятый + договор-оферта;
2. онлайн-касса / платёжный провайдер с чеками по 54-ФЗ;
3. корректная лицензия на экспорт данных — см. раздел 14.2;
4. текст отчёта без обещаний прогноза («данные OSM на <дата>, полнота зависит от сообщества»).

## 14. Юридические аспекты

### 14.1 Использование данных OSM

- Данные OSM — лицензия **ODbL 1.0**, коммерческое использование разрешено при выполнении условий.
- **Produced Work** (отрендеренная карта, тайлы, PDF-отчёт, PNG-экспорт): достаточно видимой атрибуции
  «© OpenStreetMap contributors» — ссылка на лицензию обязательна.
- **Derivative Database** (машиночитаемый экспорт POI/ячеек в CSV, GeoJSON, выгрузка базы): распространяется
  **под той же лицензией ODbL**, без технических ограничений на дальнейшее распространение. То есть платный
  экспорт POI продавать можно, но покупатель вправе переиспользовать и распространять эти данные. Это
  ограничение фиксируем в оферте, чтобы не было претензий.
- Атрибуция обязательна везде, где показываются данные: карта, легенда, PDF-отчёт, CSV (заголовок-комментарий),
  страницы с описанием данных.

### 14.2 Запреты

- Не парсим 2ГИС, Яндекс.Карты, Google Maps — ни автоматически, ни вручную.
- Не используем `tile.openstreetmap.org` в продакшене (политика OSMF, см. 5.2).
- Не смешиваем данные из источников с несовместимыми лицензиями без проверки.

### 14.3 Персональные данные

В MVP персональные данные не собираются (нет аккаунтов, нет форм с контактами). Если появятся аккаунты,
почта или телефоны — требуется политика обработки ПДн, согласие и размещение данных в РФ (152-ФЗ).

## 16. Метрики успеха MVP

| Метрика | Целевое значение (первый месяц после запуска) |
|---|---|
| Тест с предпринимателями | ≥ 5 интервью; ≥ 3 из 5 говорят «помогло сузить район поиска» |
| Визиты | ≥ 300 уникальных посетителей |
| Вовлечённость | ≥ 40% сессий с кликом по ячейке; ≥ 15% сессий со сменой категории |
| Возвраты | ≥ 10% повторных визитов за 2 недели |
| Спрос на платное | ≥ 5 заявок на разовый отчёт (до включения платежей — заявка через форму/почту) |
| Технический минимум | p95 API < 300 мс; нет инцидентов «данные старше 14 дней» |

Если по итогам метрик второго и третьего пункта провал (менее 15% кликов по ячейкам) — пересматриваем
не монетизацию, а интерфейс: скорее всего, тепловой слой не читается.

## 17. Риски и допущения

| Риск | Вероятность | Влияние | Что делаем |
|---|---|---|---|
| **Неполнота OSM** — «пустая зона» на самом деле не пустая | Высокая | Критическое: продукт даёт вредный совет | Дисклеймеры, индикатор полноты, сверка с ФНС/Росстатом в фазе 2, `fixthemap` |
| Нестабильность Overpass API | Подтверждена (наблюдали таймаут и «server too busy») | Среднее | Основной источник — Geofabrik PBF; Overpass только резерв с кэшем |
| Лицензия/стоимость подложки карты | Средняя | Высокое (может отключиться у платного сервиса) | OpenFreeMap на MVP, self-host PMTiles к прод-нагрузке |
| Категория окажется пустой в OSM (`pickup_point`) | ~~Высокая~~ **закрыт** | Среднее | Этап 0.5 пройден: минимальная категория `fitness` — 33 объекта, `pickup_point` — 501. См. `docs/recon/` |
| **Неполнота адресов в OSM** — в списке POI нечего показать построчно | Подтверждён: 32–61% объектов с полным адресом, у `pickup_point` 32% | Среднее | В UI писать «адрес не указан в OSM»; доля адресов — индикатор зрелости данных ячейки |
| Разный масштаб категорий ломает легенду (`grocery` 596 против `fitness` 46) | Высокая | Среднее | Границы классов считаются на бэкенде (`density_breaks`), а не на клиенте |
| Обязательства ODbL при платном экспорте | Высокая | Среднее (юридическое) | Явно указать в оферте и в документации отчёта |
| Один разработчик + сроки | Высокая | Среднее | Оценка 4–5 недель без буфера; отрезать по объёму, а не по качеству |
| Готовность платить 490 ₽ | Средняя | Высокое | Тест спроса до платежей: заявка через почту, 5 интервью |
| Качество адресов и дубликаты POI в OSM | Высокая | Низкое/среднее | Флаг `has_address`, дедупликация с отчётом, не удалять молча |
| Уход H3/MapLibre API (мажорные обновления) | Низкая | Среднее | Версии фиксируются lock-файлами, обновление — отдельной задачей |
| Рост трафика при бесплатной подложке | Средняя | Среднее | Кэш агрегатов, статические JSON, переход на self-host тайлов |

**Допущения:** у пользователя есть телефон/десктоп с WebGL; Geofabrik продолжает публиковать
экстракты Сибирского ФО; Томск репрезентативен для проверки гипотезы продукта; ODbL-условия не изменятся
(при изменении — пересмотр раздела 14).
